# Заметки по архитектуре (для защиты)

## Сессия 1: База данных и точка входа
- БД состоит из 6 таблиц (`users`, `tests`, `questions`, `answers`, `attempts`, `attempt_answers`), связанных внешними ключами с `ON DELETE CASCADE` для автоматического удаления дочерних записей.
- Таблица `attempt_answers` хранит конкретные `answer_id`, выбранные пользователем в рамках `attempt_id`, что позволяет поддерживать как вопросы с одним ответом (`single`), так и с несколькими (`multiple`).
- Подключение к MySQL реализовано в `backend/db.php` через `PDO` с отключённой эмуляцией подготовленных запросов (`ATTR_EMULATE_PREPARES = false`) для защиты от SQL-инъекций и сохранения числовых типов.
- Единая точка входа бэкенда — `backend/public/index.php`, раздаётся встроенным сервером PHP (`localhost:8000`).

## Сессия 2: Авторизация и роутинг
- Роутер в `backend/public/index.php` сопоставляет HTTP-метод и URI с функциями-обработчиками и перехватывает необработанные исключения в едином `try/catch`.
- Пароли хешируются через `password_hash(..., PASSWORD_DEFAULT)` и проверяются через `password_verify()`, в БД хранится только хеш.
- Авторизация построена на PHP-сессиях (`$_SESSION['user']`): при входе и регистрации вызывается `session_regenerate_id(true)` для защиты от фиксации сессии.
- Функции `requireLogin()` и `requireAdmin()` в `backend/auth.php` защищают маршруты на стороне сервера, возвращая коды 401 (не авторизован) и 403 (нет прав администратора).

## Сессия 3: Редактор тестов и загрузка изображений
- Тест создаётся (`POST /api/tests`) и обновляется (`PUT /api/tests/{id}`) одним вложенным JSON-запросом внутри PDO-транзакции (`beginTransaction` / `commit` / `rollBack`), что гарантирует атомарность записи теста, вопросов и ответов.
- Серверная валидация проверяет, что у каждого вопроса есть минимум 2 ответа, положительный вес, минимум 1 правильный ответ, а для типа `single` — ровно 1 правильный ответ.
- Если по тесту уже есть попытки в таблице `attempts`, изменение вопросов и ответов блокируется кодом `409 Conflict` (разрешено менять только название, описание и лимит попыток), чтобы не нарушать историю прохождений.
- Загрузка картинок (`POST /api/upload`) проверяет лимит размера (5 МБ), реальный MIME-тип через расширение `finfo` (белый список JPG/PNG/GIF/WEBP) и генерирует случайное имя файла через `random_bytes(16)`.

## Сессия 4: Прохождение тестов и подсчёт результатов
- Попытка фиксируется в таблице `attempts` в момент старта (`POST /api/tests/{id}/start`) с `finished_at = NULL`, тогда же проверяется лимит `max_attempts`.
- В ответе `/start` сервер выбирает из таблицы `answers` только `id` и `text` (без `is_correct`), чтобы правильные ответы нельзя было подсмотреть в браузере.
- Подсчёт баллов (`POST /api/attempts/{id}/submit`) выполняется строго на сервере: выбранные `answer_id` сверяются с правильными ответами из БД; балл равен весу вопроса (`weight`) только при точном совпадении множеств ответов.
- Выбранные пользователем варианты сохраняются в таблицу `attempt_answers`, а итоговый процент вычисляется по формуле `score / max_score * 100%`.

## Сессия 5: Каркас фронтенда и авторизация
- Фронтенд собран на React + Vite + Bootstrap без сторонних библиотек управления состоянием: текущий пользователь запрашивается при старте из `GET /api/me` в `App.jsx` и передаётся дочерним компонентам через пропсы.
- В `vite.config.js` настроен прокси для маршрутов `/api` и `/uploads` на `http://127.0.0.1:8000`, поэтому фронтенд и бэкенд работают в одном источнике (Same-Origin) и корректно обмениваются cookie `PHPSESSID`.
- Все HTTP-запросы выполняются через единую функцию `apiRequest` в `src/api.js` с параметром `credentials: 'include'`.
- Компоненты-обёртки `RequireAuth` и `RequireAdmin` ограничивают навигацию на клиенте для удобства интерфейса, дублируя серверную проверку прав (`requireLogin` / `requireAdmin`).

## Сессия 6: Редактор тестов на React
- Состояние формы теста в `TestEditorPage.jsx` хранится в одном вложенном объекте (`title`, `description`, `max_attempts`, `questions`) и отправляется одним JSON-запросом (`POST /api/tests` или `PUT /api/tests/{id}`).
- Каждому вопросу и ответу на клиенте генерируется уникальный идентификатор `uid`, который используется в атрибуте `key` вместо индекса массива для корректного добавления и удаления элементов.
- Загрузка изображения выполняется через `FormData` на `POST /api/upload`, возвращённый путь `/uploads/...` записывается в `image_path` вопроса и сразу отображается в предпросмотре.
- Если у теста флаг `has_attempts = true`, редактирование вопросов и ответов в интерфейсе блокируется, а на сервер передаются только метаданные теста.
